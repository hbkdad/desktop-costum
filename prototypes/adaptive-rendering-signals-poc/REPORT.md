# Prototypes 10 + 11 Report: Adaptive Rendering Signals

Format per the `desktop-host-prototype` skill. Covers backlog items 10 (fullscreen detection) and 11 (adaptive rendering) together, because they are the two inputs to a single decision: *should the renderer pause or degrade right now?*

- **Purpose:** Resource discipline is ranked the **#2 market gap** in `docs/research/market-gap-report.md` — every animated-wallpaper competitor researched (Wallpaper Engine, Lively, DeskScapes) draws documented CPU/GPU/battery complaints. Clearing the bar competitors already clear (a fullscreen-pause checkbox) is not enough, so these signals must be proven both *correct* and *cheap enough to poll*, not assumed.
- **Implementation:** `prototypes/adaptive-rendering-signals-poc/Program.cs` — standalone console probe, read-only. Fullscreen detection combines the supported `SHQueryUserNotificationState` API with a foreground-window-rect-vs-monitor-rect cross-check (excluding shell windows `Progman`/`WorkerW`/`Shell_TrayWnd`). Power state uses `GetSystemPowerStatus` (AC line status, battery presence/percent, and `SystemStatusFlag` for battery saver). Samples 5 times over ~5s and times each sample.
- **Test method:** Built and run twice against the live desktop — once with a naive rect-only heuristic, once after fixing the defect that first run exposed (below).
- **Measurements / findings:**
  - **A real false positive was found and fixed.** The first run reported `renderer should pause: True` while the foreground window was merely a **maximized** (not fullscreen) application window. A maximized window covers the entire monitor rect — especially here, where the work area equals the monitor bounds (no taskbar reservation, corroborating Prototype 9's incidental finding). Left unfixed, this would pause wallpaper/widget rendering during **ordinary desktop use**, which is a worse user-visible bug than not pausing at all.
  - **The supported API was right; the hand-rolled heuristic was wrong.** `SHQueryUserNotificationState` correctly returned `QUNS_ACCEPTS_NOTIFICATIONS` (5, not fullscreen) in both runs, while the rect comparison produced the false positive. This is a concrete, empirical instance of the project's own non-negotiable principle ("prefer supported Windows APIs") paying off, and is the strongest reason to make the documented API authoritative rather than a heuristic.
  - **Fix verified:** excluding maximized windows (`GetWindowPlacement` → `SW_SHOWMAXIMIZED`) eliminated the false positive on re-run — the same window now correctly reports `maximized, not fullscreen` and `renderer should pause: False`. Borderless-fullscreen games are normally *not* maximized, so this exclusion removes the false positive without losing the case that matters.
  - **Cost:** ~0.53–0.86 ms per combined check in steady state (the ~12.6 ms first sample is JIT warm-up, not representative; the printed 3.08 ms average is skewed by it and should not be quoted as the real figure). At roughly 0.7 ms, polling this signal once or twice a second is negligible against the rendering it gates — though an event-driven approach would still be preferable to polling where available.
  - **Power state:** API plumbing verified working — AC line status `1` (plugged in), battery saver flag readable, all fields parsed correctly.
- **Limitations:** **This machine has no battery** (`Battery present: False`), so the on-battery and battery-saver degradation paths **could not be exercised** — only that the API returns and parses correctly. Given the Battery-Conscious Laptop User is an MVP-primary persona (`docs/product/personas.md` #2), this must be validated on real laptop hardware before the resource-discipline claim can be made in earnest. Also: no actual fullscreen game/presentation was running during the test, so `QUNS_RUNNING_D3D_FULL_SCREEN` (3) and `QUNS_PRESENTATION_MODE` (4) were never observed being returned — only the negative case was confirmed. Polling was used rather than event-driven notification (`SetWinEventHook` / power-notification registration), which is what production should prefer.
- **Recommendation:** Make `SHQueryUserNotificationState` the authoritative fullscreen signal; use the rect check only as a secondary confirmation and only with the maximized-window exclusion applied. For power, treat `ACLineStatus == 0 || SystemStatusFlag == 1` as the degrade trigger. Move to event-driven notification rather than polling before shipping. Validate both the true-fullscreen positive case and the on-battery path on appropriate hardware.
- **Keep/discard decision:** **Keep.** Both signals are cheap, and the detection logic (including the maximized-window exclusion, which a naive implementation would get wrong) is directly reusable in the wallpaper/widget host. The two unvalidated cases are explicitly recorded rather than assumed working.

## Impact on other project artifacts

- Supplies the first real measurement (~0.7 ms/check) toward the performance budgets scoped in `backlog/dependency-register.md` and the `performance-test` skill.
- The maximized-vs-fullscreen distinction should become a **regression test** once the renderer exists — it is exactly the class of bug that would generate the "pauses when it shouldn't / doesn't pause when it should" complaints seen across competitors.
- Two hardware-dependent validation gaps (no battery, no second monitor) now span Prototypes 9–11 and are tracked in `backlog/risk-register.md`.
