# Prototype 2, Spike B Report: Static Wallpaper Fallback (SPI_SETDESKWALLPAPER)

Format per the `desktop-host-prototype` skill. Follow-up to Prototype 2 (`prototypes/desktop-overlay-fallback-poc/REPORT.md`), which found z-order-based overlay placement cannot get behind Progman/desktop icons on this build.

- **Purpose:** Prove the guaranteed-available, tier-of-last-resort fallback: setting rendered content as the actual OS desktop wallpaper via the fully-supported `SystemParametersInfo(SPI_SETDESKWALLPAPER)` API, which sidesteps Z-order entirely (there's nothing to race or lose a position fight against).
- **Implementation:** `prototypes/desktop-static-wallpaper-fallback-poc/Program.cs` — standalone console/WinForms-referencing app (System.Drawing for bitmap generation). Reads the current wallpaper path first, generates a placeholder bitmap into the temp folder, sets it as wallpaper, reads back to confirm, then **always restores the original wallpaper path in a `finally` block** and deletes the temp file — safe even on a crash mid-probe.
- **Test method:** Built and run against the live desktop. Verified three ways: (1) the API call's own return value, (2) an immediate read-back via `SPI_GETDESKWALLPAPER` compared against the path set, (3) an independent post-hoc check of the `HKCU:\Control Panel\Desktop\Wallpaper` registry value after the probe exited, confirming the original user wallpaper (`...\Gemini_Generated_Image_oqxv17oqxv17oqxv.png`) was back in place.
- **Measurements / findings:** `SPI_SETDESKWALLPAPER` returned `True`; read-back path matched the generated bitmap exactly; restore call returned `True` and was independently confirmed via the registry. Total round-trip (set → 1.5s hold → restore) completed in under 2 seconds. No errors, no leftover temp file, no leftover wallpaper change. Windows build tested: `10.0.26200.0`.
- **Limitations:** Static image only — this API does not support animation/video, so it cannot deliver the "video/animated wallpaper" job-to-be-done on its own; it exists purely as the always-works safety net when tiers 1 (WorkerW) and 2 (z-order overlay, now discarded per Prototype 2) aren't available or aren't appropriate (e.g. explicit battery-saver/safe mode). `.bmp` format was used for maximum compatibility; did not test `.jpg`/`.png` paths, multi-monitor per-screen wallpaper (a separate, also-supported but different API — `IDesktopWallpaper` COM interface — would be needed for true per-monitor assignment), or slideshow/rotation behavior.
- **Recommendation:** Adopt as the permanent tier-3 fallback in the wallpaper host module. For multi-monitor per-screen wallpaper specifically, a follow-up spike should evaluate the `IDesktopWallpaper` COM interface (also a supported, documented Windows API) rather than the older `SPI_SETDESKWALLPAPER` call, which only supports a single wallpaper spanning all monitors.
- **Keep/discard decision:** **Keep — this is the proven, permanent safety-net tier.** Combined with Prototypes 1 and 2's results, the desktop-hosting strategy is now: WorkerW attach when detectable (opportunistic, unreliable) → static `SystemParametersInfo`/`IDesktopWallpaper` fallback (proven reliable, static content only) → z-order overlay window repurposed as a front-layer widget/HUD surface, not a wallpaper surface.

## Impact on other project artifacts

- This closes out the "recommended first three" prototypes' desktop-hosting question with a concrete, evidence-based three-tier design, ready for an ADR.
- `docs/product/prd.md` §2 (non-goals) already defers shader/particle/web wallpapers past MVP; this finding suggests **video wallpaper itself may need explicit "requires WorkerW attach; falls back to static image" framing** in the MVP acceptance criteria (§13) rather than being assumed universally available — a product-level implication, not just a technical footnote.
