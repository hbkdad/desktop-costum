# Prototype 3 Report: Explorer Restart Recovery

Format per the `desktop-host-prototype` skill.

- **Purpose:** Prove that an explorer.exe restart can be detected programmatically, that window handles obtained before the restart (Progman, and by extension any Tier-1 WorkerW attachment per ADR-0003) become stale and must be re-acquired, and measure real recovery timing — the second most common cross-competitor failure mode found in `docs/research/competitor-matrix.md` (Fences, Start11, DisplayFusion, Lively Wallpaper all have documented Explorer crash/restart-loop complaints).
- **Implementation:** `prototypes/explorer-restart-recovery-poc/Program.cs` — standalone console app. Records Progman's handle, open File-Explorer (`CabinetWClass`) window count, and `explorer.exe` PID(s) before; kills all `explorer.exe` processes; immediately relaunches `explorer.exe`; polls for a new Progman window (15s timeout); re-checks all the same measurements after.
- **Test method:** Run directly against the live desktop session (the only way to test this meaningfully). This is more disruptive than Prototypes 1/2 — the taskbar and desktop icons disappear for the duration of the restart — so the probe checked for open File Explorer windows first and minimized downtime by relaunching immediately rather than waiting on any OS auto-recovery. Verified clean end-state afterward with an independent `Get-Process explorer` check.
- **Measurements / findings:**
  - Progman handle changed as expected (`0x10168` → `0x2026A`); the old handle failed an `IsWindow` check afterward (confirmed stale/invalid) — validates the core hypothesis that any code holding a Tier-1 handle must detect the restart and re-acquire, not assume the handle stays valid indefinitely.
  - New Progman window appeared **2666 ms** after the kill — a real number for how long a "black desktop" gap could last if recovery depends solely on this probe's own relaunch call.
  - **Unexpected finding:** after our explicit relaunch, there were briefly **two** `explorer.exe` processes (the original PID reappearing alongside a new one), and the File-Explorer-window count that was 1 before was *also* 1 immediately after — both signs that **Windows' own newer auto-recovery mechanism raced with our manual relaunch.** Plausible mechanism: Windows 11 now appears to auto-restart `explorer.exe` on its own shortly after a forceful kill (plausibly related to the same shell-resilience work behind the Windows 11 24H2 fixes for the wallpaper-app compatibility hold found in `docs/research/competitor-matrix.md`); our own `Process.Start("explorer.exe")` call then landed *after* the shell was already back, and because `explorer.exe` with no arguments opens a new folder window when a shell is already running (rather than becoming the shell), it likely reopened a stray Explorer window instead of being a no-op.
  - The situation self-resolved: a follow-up check ~a minute later found exactly **one** `explorer.exe` process (`PID 13300`) with no visible window title — i.e., no lingering stray Explorer window, clean end-state. No manual cleanup was needed.
  - Windows build tested: `10.0.26200.0` (same as the earlier prototypes).
- **Limitations:** Single run, single machine. Did not measure recovery time *without* our own relaunch call (to isolate how fast Windows' own auto-recovery alone is) — that's the obvious next measurement. Did not test what happens to a live Tier-1 WorkerW-attached rendering window specifically (no such attachment exists yet to test against, per Prototype 1's result) or a live Tier-3 widget/HUD overlay window across a restart.
- **Recommendation:** The recovery adapter should **not** unconditionally kill-and-relaunch `explorer.exe` as its own recovery action for a *detected* crash (as opposed to *deliberately restarting* it) — it should poll briefly for Progman's reappearance first, since Windows may already be handling it, and only relaunch if that doesn't happen within a short timeout. This avoids the duplicate-process/stray-window race observed here. Whatever the trigger, the adapter must treat all previously-held Tier-1 handles as invalid the moment a restart is detected and re-run handle acquisition from scratch — confirmed necessary by this test, not just assumed.
- **Keep/discard decision:** **Keep.** Concrete, reusable finding: build the recovery watcher to detect-then-wait-then-relaunch, not kill-then-immediately-relaunch. This directly informs the desktop host module's crash-recovery design (`docs/architecture/adr/` — a follow-up ADR once the watcher is built) and should also inform the workspace/layout persistence design (Slice 6 in the master plan) — anything holding process-lifetime state tied to the old Explorer session needs the same "assume invalid, reacquire" pattern proven here for Progman.

## Impact on other project artifacts

- Corroborates `docs/research/market-gap-report.md`'s #1 priority (shell-update resilience) with direct evidence: even a deliberate, clean restart triggered by this probe produced an unexpected race condition with the OS's own recovery behavior. A less careful implementation could easily have made things worse (more duplicate processes, more stray windows) rather than better.
- `backlog/prototype-backlog.md` and `.agents/state/decisions.md` updated with this finding and the detect-then-wait-then-relaunch recommendation.
