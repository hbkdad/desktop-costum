# Prototype 2 Report: Desktop Overlay Fallback

Format per the `desktop-host-prototype` skill.

- **Purpose:** Prove a rendering path for wallpaper/widget content that does not depend on the undocumented WorkerW/Progman technique (Prototype 1 found that technique unreliable on the current build), since the non-negotiable principles require a working fallback independent of undocumented shell behaviour.
- **Implementation:** `prototypes/desktop-overlay-fallback-poc/Program.cs` — a standalone WinForms probe (not part of `DesktopRuntime.slnx`). Creates a borderless, non-activating, click-through (`WS_EX_TRANSPARENT | WS_EX_NOACTIVATE | WS_EX_TOOLWINDOW`), full-primary-monitor window, then calls `SetWindowPos(hwnd, HWND_BOTTOM, ...)`. Auto-closes after ~4 seconds; no window is left running.
- **Test method:** Built and run against the live interactive desktop session via `dotnet run`. Verification is programmatic, not visual: the probe re-enumerates all top-level windows (`EnumWindows`) both immediately after showing and just before closing, and compares its own position in that Z-order list to Progman's position (lower index = more toward the front/top).
- **Measurements / findings:**
  - Immediately after `Show()` + `SetWindowPos(HWND_BOTTOM)`: overlay at Z-order index 14 of 372, Progman at index 247 — overlay was far in *front* of Progman at this point (the `HWND_BOTTOM` call in `OnShown` appears to race with WinForms' own window-activation z-order changes).
  - Just before close (~4s later, no further explicit repositioning): overlay had drifted to index 245 of 372, Progman still at 247 — much closer to the bottom, but **still 2 positions in front of, i.e. above, Progman**, not behind it.
  - In both measurements, the overlay never achieved a Z-order position behind Progman. `HWND_BOTTOM` appears to push a normal top-level window toward, but not past, the shell/desktop window — consistent with Windows reserving the true bottom of the Z-order for the shell itself rather than letting an arbitrary application claim a position below it.
  - Windows build tested: `10.0.26200.0` (same machine/build as Prototype 1).
- **Limitations:** Did not test whether Progman/`SHELLDLL_DefView` paints an opaque full-screen background that would hide content behind it even if z-order placement succeeded. Single monitor, no multi-monitor test.
- **Spike A (same session, follow-up):** Retried using `SetWindowPos(hwnd, progmanHandle, ...)` — Progman's *real* window handle as `hWndInsertAfter`, instead of the `HWND_BOTTOM` pseudo-value — plus a re-assertion 1.5s after first show (real wallpaper apps periodically re-assert position). **Same result**: overlay settled at index 245 of 372, Progman still at 247, in both the initial and re-asserted measurements. Confirms this is not a `HWND_BOTTOM`-specific quirk — Windows does not allow a normal top-level window to be positioned behind the shell/desktop window via `SetWindowPos`, regardless of which reference handle is used.
- **Recommendation:** A plain top-level window **cannot** be placed behind Progman via `SetWindowPos`, with either the `HWND_BOTTOM` pseudo-value or Progman's real handle. Z-order tricks alone are a dead end for this goal. The remaining path for guaranteed behind-icons rendering is `SystemParametersInfo(SPI_SETDESKWALLPAPER, ...)` — the actual supported OS wallpaper-setting API — which sidesteps z-order entirely by replacing the desktop background image itself. Tested separately; see `prototypes/desktop-static-wallpaper-fallback-poc/REPORT.md`.
- **Keep/discard decision:** **Discard z-order-based overlay as a "behind icons" strategy entirely** (both `HWND_BOTTOM` and real-handle variants). Keep the click-through/non-activating window *shape* (border style, extended styles) as a reusable building block for a different purpose: an **in-front, click-through HUD/widget layer** that sits above normal desktop content but below/never-steals-focus from real application windows — useful for widgets, not for "wallpaper behind icons." The wallpaper-behind-icons problem is now solely addressed by WorkerW attach (opportunistic, Prototype 1) and the static fallback (see below).

## Impact on other project artifacts

- Neither Prototype 1 (WorkerW attach) nor either variant of Prototype 2 (z-order overlay, `HWND_BOTTOM` or real-handle) reliably achieves "behind icons" rendering on this build. This is a more significant finding than originally scoped for the "recommended first three" — the wallpaper host module's only remaining behind-icons paths are WorkerW attach (opportunistic/unreliable) and the static `SystemParametersInfo` fallback (always available, static content only). There is currently no tested path for *reliable animated/video* wallpaper behind icons on this build — that itself is a significant product-scoping finding, not just an implementation detail.
- `backlog/prototype-backlog.md` and `backlog/risk-register.md` updated accordingly.
- This is now ready for an ADR: the desktop-hosting strategy is WorkerW-attach-when-available with a hard drop to static-image fallback when not, and the "overlay window" concept is repurposed for widgets (front layer), not wallpaper (back layer).
