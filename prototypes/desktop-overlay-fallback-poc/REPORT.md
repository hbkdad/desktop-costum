# Prototype 2 Report: Desktop Overlay Fallback

Format per the `desktop-host-prototype` skill.

- **Purpose:** Prove a rendering path for wallpaper/widget content that does not depend on the undocumented WorkerW/Progman technique (Prototype 1 found that technique unreliable on the current build), since the non-negotiable principles require a working fallback independent of undocumented shell behaviour.
- **Implementation:** `prototypes/desktop-overlay-fallback-poc/Program.cs` — a standalone WinForms probe (not part of `DesktopRuntime.slnx`). Creates a borderless, non-activating, click-through (`WS_EX_TRANSPARENT | WS_EX_NOACTIVATE | WS_EX_TOOLWINDOW`), full-primary-monitor window, then calls `SetWindowPos(hwnd, HWND_BOTTOM, ...)`. Auto-closes after ~4 seconds; no window is left running.
- **Test method:** Built and run against the live interactive desktop session via `dotnet run`. Verification is programmatic, not visual: the probe re-enumerates all top-level windows (`EnumWindows`) both immediately after showing and just before closing, and compares its own position in that Z-order list to Progman's position (lower index = more toward the front/top).
- **Measurements / findings:**
  - Immediately after `Show()` + `SetWindowPos(HWND_BOTTOM)`: overlay at Z-order index 14 of 372, Progman at index 247 — overlay was far in *front* of Progman at this point (the `HWND_BOTTOM` call in `OnShown` appears to race with WinForms' own window-activation z-order changes).
  - Just before close (~4s later, no further explicit repositioning): overlay had drifted to index 245 of 372, Progman still at 247 — much closer to the bottom, but **still 2 positions in front of, i.e. above, Progman**, not behind it.
  - In both measurements, the overlay never achieved a Z-order position behind Progman. `HWND_BOTTOM` appears to push a normal top-level window toward, but not past, the shell/desktop window — consistent with Windows reserving the true bottom of the Z-order for the shell itself rather than letting an arbitrary application claim a position below it.
  - Windows build tested: `10.0.26200.0` (same machine/build as Prototype 1).
- **Limitations:** Only tested `HWND_BOTTOM` as the insertion point; did not test `SetWindowPos` with Progman's actual window handle as the `hWndInsertAfter` reference (a real handle, not the `HWND_BOTTOM` pseudo-value, may behave differently and is the obvious next thing to try). Did not test whether Progman/`SHELLDLL_DefView` paints an opaque full-screen background that would hide content behind it even if z-order placement succeeded — if it does, z-order tricks alone can't produce a true "behind icons" look regardless of position. Single run, single monitor, no multi-monitor test.
- **Recommendation:** A plain top-level window pushed via `HWND_BOTTOM` is **not sufficient on its own** to render behind desktop icons. Two concrete follow-ups, neither attempted yet: (1) retry `SetWindowPos` using Progman's real handle as `hWndInsertAfter` instead of the `HWND_BOTTOM` constant; (2) treat the fully-supported `SystemParametersInfo(SPI_SETDESKWALLPAPER, ...)` API — rendering content to a bitmap and setting it as the literal OS wallpaper — as the *guaranteed-available* fallback tier for static/slow-changing content, independent of any z-order or WorkerW trickery, since it cannot fail the way both attachment strategies tested so far have shown fragility.
- **Keep/discard decision:** **Keep, revise.** This specific implementation (bare `HWND_BOTTOM`) is discarded as insufficient by itself. The next spike should try the Progman-handle-as-insert-after variant and, in parallel, build the `SystemParametersInfo` static-image fallback as the tier-of-last-resort that is provably always available — giving the wallpaper host module three tiers (WorkerW attach → z-order-behind-Progman overlay → SPI_SETDESKWALLPAPER static fallback) instead of a single fallback.

## Impact on other project artifacts

- Neither Prototype 1 (WorkerW attach) nor Prototype 2 as tested (z-order overlay) reliably achieves "behind icons" rendering on this build. This is a more significant finding than originally scoped for the "recommended first three" — it means the wallpaper host module needs a three-tier fallback chain, not a two-tier one, and the always-available tier (`SystemParametersInfo`) only supports static/slow-changing content, which has product implications (e.g., a laptop-battery-safe "static fallback" mode may end up being the *default* experience on some builds, not an edge case).
- `backlog/prototype-backlog.md` and `backlog/risk-register.md` updated accordingly.
- This should become an ADR once the Progman-handle-as-insert-after variant is tried — right now there isn't yet a working "behind icons" solution to lock in, undocumented or otherwise.
