# Prototype 1 Report: Desktop Attachment (WorkerW technique)

Format per the `desktop-host-prototype` skill.

- **Purpose:** Determine whether the well-known (undocumented) Progman/WorkerW technique — used by Wallpaper Engine, Lively Wallpaper, and similar tools — can reliably locate the desktop-icon-layer sibling window on a current Windows 11 build, as a prerequisite for any wallpaper/widget rendering behind desktop icons.
- **Implementation:** `prototypes/desktop-attachment-poc/Program.cs` — a standalone, isolated console app (not part of `DesktopRuntime.slnx`). Sends the undocumented `0x052C` message to the `Progman` window, then enumerates top-level windows for the one hosting `SHELLDLL_DefView` and searches for a `WorkerW`-class sibling after it in Z-order (the standard published algorithm, matching known open-source reference implementations). Read-only: no window is reparented or drawn into.
- **Test method:** Built and run directly against the live interactive desktop session (not CI/headless) via `dotnet run`, twice — once with the naive `GetWindow(GW_HWNDNEXT)` sibling check, once with the more robust `FindWindowEx(NULL, hWnd, "WorkerW", NULL)` lookup used by known-working reference implementations. Added a diagnostic enumeration of all top-level windows with "Worker" or "Progman" in the class name on failure.
- **Measurements / findings:**
  - `Progman` was found reliably (`0x10168`), and `SHELLDLL_DefView` was found as its own child (not a separate WorkerW's child) — consistent with modern Windows behavior where the icon view sometimes lives directly under Progman pre-message.
  - Neither sibling-lookup strategy found a `WorkerW` positioned immediately after `Progman` in Z-order after sending `0x052C`.
  - The diagnostic dump found **15 separate top-level `WorkerW`-class windows already present** on the system, none positioned where the classic technique expects the freshly-spawned one. `Progman` enumerates *last* (bottommost in Z-order) among top-level windows, which is structurally why "the next window after Progman" was empty in both runs — nothing else needed to intervene for the lookup to fail; the technique instead depends on `0x052C` inserting a new window immediately above Progman, which was not observed to happen (or happened asynchronously outside this probe's synchronous `SendMessageTimeout` call).
  - Windows build tested: `10.0.26200.0` (current Windows 11 24H2/25H2-era build on this machine, per `Environment.OSVersion`).
- **Limitations:** Single build tested, single machine, single run pattern (no retry/delay loop after the message, no window-creation event hook, no disambiguation of the 15 pre-existing `WorkerW` windows by owner process/size/visibility). Did not test on an older Windows 11 build for comparison. Did not attempt the alternative technique of drawing directly into the `Progman`-owned `SHELLDLL_DefView` parent itself (some reference implementations fall back to this when the WorkerW spawn doesn't happen).
- **Recommendation:** Do not treat WorkerW-based attachment as reliably available on current Windows 11 builds without further, more careful disambiguation work (event-driven detection of the newly created window, or process/size-based filtering of the existing WorkerW set). This result is directly consistent with the Windows 11 24H2 breakage pattern already documented for Wallpaper Engine, Lively Wallpaper, and others in `docs/research/competitor-matrix.md` — i.e., this isn't a one-off implementation bug in this probe, it's corroborating evidence that the whole technique class has gotten less deterministic on recent Windows builds.
- **Keep/discard decision:** **Keep, but demote from primary to opportunistic-enhancement.** The desktop overlay fallback (Prototype 2) should be treated as co-primary rather than a true fallback-of-last-resort, per the non-negotiable principles' own requirement (`AGENTS.md`: "maintain safe fallbacks"). A follow-up spike (not scheduled yet) could revisit WorkerW attachment with `SetWinEventHook`-based detection of window creation instead of a synchronous post-message enumeration, if the overlay fallback proves visually/functionally insufficient on its own.
