# Decision Log

Compact log, newest first. Full rationale for architectural decisions belongs in `docs/architecture/adr/`, not here.

- **2026-08-02** — Workspace schema v1 designed and implemented (`docs/architecture/workspace-schema.md`, `src/DesktopRuntime.Core/Workspaces/`). Key rules: monitors identified by device interface path only; container/widget bounds stored **monitor-relative**, not virtual-desktop-global; wallpaper records what was *requested*, never which tier served it (a degraded state must not become sticky); newer-schema files are **rejected outright** rather than partially parsed; layouts for disconnected monitors are deferred, never discarded. *Why:* each rule follows from a Phase 3 prototype result or ADR-0003 — see the rationale section of the schema doc. 14 tests passing.
- **2026-08-02** — Fullscreen detection must treat `SHQueryUserNotificationState` as **authoritative**, with foreground-rect comparison only as a secondary check that explicitly excludes **maximized** windows. *Why:* Prototype 10 (`prototypes/adaptive-rendering-signals-poc/REPORT.md`) found a naive rect-only heuristic flags a maximized window as fullscreen, which would pause rendering during ordinary desktop use; the supported API returned the correct answer where the heuristic did not. *How to apply:* make the maximized-vs-fullscreen distinction a regression test once the renderer exists. Steady-state cost of the combined check is ~0.7 ms.
- **2026-08-02** — Monitor identity is persisted on the **device interface path** (embeds hardware/EDID id), never on `\\.\DISPLAYn` or `HMONITOR`; resolution/position/DPI are *attributes of* an identified monitor, not part of its identity. Per-monitor DPI awareness must be set at process start, before any geometry is read. *Why:* Prototype 9 (`prototypes/monitor-dpi-persistence-poc/REPORT.md`). *Caveat:* reconnect stability is structurally sound but **not empirically verified** — no second monitor on the test machine.
- **2026-08-02** — Explorer-restart recovery adapter must **detect-then-wait-briefly-then-relaunch**, not kill-then-immediately-relaunch. *Why:* Phase 3 Prototype 3 (`prototypes/explorer-restart-recovery-poc/REPORT.md`) found Windows 11 appears to have its own auto-recovery for a killed `explorer.exe`; an immediate manual relaunch raced with it and produced a transient duplicate process / stray Explorer window (self-resolved, but avoidable). Also confirmed: Progman's handle goes stale on restart and must be re-acquired, not assumed valid (~2.7s observed recovery time for a manual kill+relaunch).
- **2026-08-02** — **Desktop hosting strategy finalized**, see [ADR-0003](../../docs/architecture/adr/0003-desktop-hosting-strategy.md): Tier 1 WorkerW attach (opportunistic, animated content) → Tier 2 static wallpaper API (`SystemParametersInfo`/`IDesktopWallpaper`, guaranteed, static-only) → z-order overlay window repurposed for front-layer widgets/HUD, not wallpaper (z-order-behind-Progman placement is structurally impossible for a normal window, confirmed with both `HWND_BOTTOM` and Progman's real handle). *Why:* four prototypes/spikes run against the live desktop this session (`prototypes/desktop-attachment-poc`, `prototypes/desktop-overlay-fallback-poc` + Spike A, `prototypes/desktop-static-wallpaper-fallback-poc` = Spike B) — see each `REPORT.md`. *How to apply:* video/animated wallpaper is opportunistic, not guaranteed; PRD §4/§13 updated accordingly.
- **2026-08-02** — MVP scope targets personas #1-3 (Multi-Monitor Power User, Battery-Conscious Laptop User, Desktop Organizer) and defers Aesthetic Tinkerer (creator tooling) and IT-Managed (fleet deployment) past MVP. *Why:* `docs/product/problem-ranking.md` ranks shell-update resilience and resource discipline above consolidation/creator-economy for MVP-stage risk/reward; see `docs/product/mvp-positioning.md`.
- **2026-08-02** — Solution uses the SDK's new `.slnx` solution format (`DesktopRuntime.slnx`), not `.sln` — `dotnet new sln` on the installed .NET 10 SDK (10.0.204) generates `.slnx` by default. CI and docs reference `.slnx`. *Why:* matches what the installed toolchain actually produces; avoids a stale/wrong reference.
- **2026-08-02** — Minimal `src/DesktopRuntime.Core` (net10.0 class library) + `tests/DesktopRuntime.Core.Tests` (xUnit) skeleton created and verified to build and test green, satisfying the Phase 0 requirement that the repo can build/test before feature work starts. *Why:* explicit Phase 0 gate; net10.0 chosen because it's what the installed SDK targets by default (current supported release per the non-negotiable principles).
- **2026-08-02** — Product name unresolved; `Desktop Runtime` is an internal placeholder only. Forge-related names/branding/themes are permanently excluded. *Why:* explicit project constraint.
- **2026-08-02** — Provisional technology baseline (C#, current .NET, WinUI 3, Windows App SDK, SQLite, WebView2, Direct3D/Win2D, MSIX) accepted as a starting point, not locked. See [ADR-0002](../../docs/architecture/adr/0002-provisional-technology-baseline.md). *Why:* must be verified per Phase 3 prototypes before Phase 4 architecture lock.
- **2026-08-02** — Electron is excluded unless a future ADR justifies it in writing against the provisional baseline. *Why:* explicit non-negotiable principle; memory/packaging/native-integration cost.
- **2026-08-02** — No kernel drivers, DLL injection, or unrestricted global hooks in the initial product. *Why:* explicit non-negotiable principle; keeps the trust boundary at AppContainer/process-isolation level.
- **2026-08-02** — Repository scaffolded at `github.com/hbkdad/desktop-costum`. Phase 0 files authored locally but not committed or pushed pending owner review. *Why:* commits/pushes require explicit user confirmation.
